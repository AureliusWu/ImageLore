# Windows 恢复事务：对象所有权与中断续作

日期：2026-10-20（Asia/Shanghai）。本文记录 v0.26.0 独立候选源码的 Windows 后端修复与本地验收。它没有发布新的桌面程序，也不代表 main、远程 CI、安装升级或真实桌面恢复验收已经完成。

本修复覆盖最终资料库替换与新协议事务续作。`finish_pending_stage`、`stage_restore_at` 的旧候选暂存入口尚未完成相同的所有权事务与并发修复；下文四个原始反例不覆盖这两个入口。恢复安全的 A1/A2 门槛继续开放。

## 已复现的四个丢失窗口

旧实现的最终写入检查结束后会释放锁，后续路径移动与回滚无法证明文件仍属于本次恢复。四个真实 SQLite / 文件系统回调反例均先执行独立正常恢复对照，再触发冲突；不是仅凭静态审查推断。

| 反例 | 旧实现的实际失败 | 当前候选的验收边界 |
| --- | --- | --- |
| A：最终损坏复核后修好活动库 | 回调成功修复并关闭资料库，恢复仍覆盖刚修好的内容 | 最终持锁前的修复会被重新观察，自动恢复停止；最终持锁后的修复尝试实际被拒绝，此时没有产生一笔“后来提交” |
| B：原件移入保留区后，新建同名活动库 | 安装暂存库覆盖新建活动库 | 新建文件原样保留，安装停止；原始 pending、raw、保留区原件与 staged 同时保留 |
| C：同一位置新建活动库后注入错误 | 回滚移走并清理外来活动库，再恢复旧原件 | 回滚发现不属于本事务的对象便停止，保留双方及恢复证据 |
| D：安装之后、回滚之前提交新内容 | 在已安装文件中真实提交的新内容被旧回滚删除 | 当前安装句柄仍持有时，写入尝试实际被拒绝；另有中断续作回归验证同一 File ID 上内容已改变时停止，不删除那笔新内容 |

四个原始 RED 的源码、测试 EXE 与失败日志冻结保存在仓库外。当前 GREEN 会区分“写入成功后必须保留”与“写入被操作系统拒绝，未产生新内容”，没有把后者记为已产生的新提交被保全。

## 新协议的文件与所有权

Windows 最终替换使用数据目录内的 `restore.transaction`，与旧 `restore.rollback` 分开。事务目录只识别 `PREPARED.json`、`COMMITTED`、`staged`、`database`、`wal`、`shm` 六个角色；出现其他内容即停止保留。

`owned_handle.rs` 负责持续持有文件对象，`guarded_restore.rs` 负责准备与安装，`restore_journal.rs` 负责严格记录编解码，`guarded_resume.rs` 负责重新获取对象后的回滚或已提交清理。它们使用以下证据：

- 文件指纹同时记录卷序列号、File ID、SHA-256、长度与修改时间。同一 File ID 上的新 SQLite 提交仍会使完整指纹不匹配，不能仅凭名称或 File ID 删除。
- DB、WAL、SHM 按明确角色取得句柄；取得失败会释放已经取得的句柄并停止。不存在的辅助文件名称没有被锁住，之后若出现新 WAL/SHM，必须停止并保留，不能当作本次恢复的附件处理。
- 数据目录、事务目录以及 raw 保全目录的父目录持续持有目录句柄，拒绝重解析点与路径越界。目录持锁保护目录身份，仍允许正常创建子文件，不等于锁住全部子名称。
- 事务目录使用父目录句柄下的原子“只创建新目录”操作；已有同名目录不会被认领。文件移动使用已持有的同一对象句柄，并要求目标不存在；不以“检查后再覆盖”的路径重命名代替。
- raw 是保全证据，记录相对数据目录的路径及完整指纹。它不授予删除任何任意路径的权限；续作必须先持有 raw 及其父目录并核实证据，才能清理对应保留区原件。

## 一次替换的顺序

1. 先处理已有新协议事务。任何无法安全续作的现场都会阻止本轮继续，避免叠加第二笔恢复。
2. 持有恢复候选及其 DB/WAL/SHM，制作一次性 SQLite 检查副本。检查和 `VACUUM INTO` 在副本上执行，避免 SQLite 在源候选目录重建辅助文件。暂存目标先独占创建，供 SQLite 生成时释放，生成后重新取得并核对原对象身份，再校验并同步文件。
3. 获取原活动库角色、保全 raw、执行初步检查。初步检查之后到最终获取之间允许原库改变；最终重新获取完整角色，重新比较指纹，必要时重新保全 raw，并在持锁副本上复核。这一阶段观察到健康修复会停止自动恢复。版本不支持、不可用或无法确认损坏也不能授权自动覆盖。
4. 最终复核之后，已经取得的原件句柄持续持有。使用已持有对象生成的 raw 副本须先同步、关闭并重新取得，再核实身份与内容，记录稳定的修改时间；raw 父目录句柄继续保留。
5. `PREPARED.json` 以只创建新文件的方式写入并同步，之后才移动任何原件。记录包括格式版本、事务 token、数据与事务目录身份、恢复模式、原 DB/WAL/SHM 指纹、staged 指纹、pending 角色及 raw 证据；解析同时检查长度上限、校验和、字段、路径和角色约束。
6. 按已持有的角色把原件逐个移至事务目录的 `database`、`wal`、`shm`，每次均禁止替换目标。再确认活动名称及其辅助名称没有新对象，以同一句柄把 staged 安装到活动名称；目标被占用时原子移动失败并保留双方。
7. 已安装文件继续持有独占句柄，完整业务 schema 检查在它的副本上进行。检查成功且完整指纹仍匹配后，才写入并同步 `COMMITTED`。这是多步应用恢复协议，不是把 DB/WAL/SHM 合成一次操作系统原子移动。
8. 释放本轮对象后，续作逻辑重新获取全部角色并重验记录。释放间隙出现的新提交或新对象必须使续作停止，不能沿用先前检查结果授权清理。已提交事务只走已提交清理，不因清理失败回滚已提交安装。

`COMMITTED` 自含完整 Prepared payload，并校验 token、payload 与校验和的绑定。清理先处理已匹配的保留区原件和待消费 pending，再删除 `PREPARED.json`，最后删除 `COMMITTED`；因此准备记录已删除、提交记录尚存时仍可续作。raw 永久保留在保全目录。事务目录最后仅通过已核实的目录句柄删除空目录，不递归清除未知内容。

## 中断、冲突与再次启动

| 再次检查的状态 | 行为 |
| --- | --- |
| 只有有效 Prepared，尚未提交，全部原件与 staged 能按角色匹配 | 按已持有对象执行禁止覆盖的回滚，保留 pending 与 raw；原件已归位、staged 已清理的部分完成状态也能继续 |
| 有有效 Commit，包括只剩 Commit 的部分清理状态 | 核实安装库、保留区、pending 与 raw 后继续清理；允许已合法删除的角色缺失，不允许出现替代对象 |
| 外来活动库、同一 File ID 上的新内容、外来 WAL/SHM | 停止，保留活动内容、事务与原件；资料库能够正常打开也不构成删除授权 |
| 记录截断、未知字段或格式、校验和不符、目录身份不符、raw 不匹配或路径越界 | 停止，保留现场，不猜测谁是原件 |
| 没有记录但事务目录非空 | 停止并保留；只有实际空目录才允许按持有目录身份删除 |

B/C 的回归除检查实际 marker、额外资产和错误结果外，还收集活动库、pending、raw、保留区、staged 与记录文件的字节和修改时间，在两次再次启动处理中逐一比较未变。另有新 WAL 出现的保全回归。恢复被拒绝时，原始文件留存本身是结果，不能只用返回 `Err` 代替这些断言。

释放句柄后另有真实 SQLite 提交回归，分别覆盖“安装后尚未提交便失败”与“提交记录已同步”两条收尾路径。回调在同一已安装对象中提交新 marker 和第二笔资产，明确比较 File ID 不变及 SHA 改变；正式续作与随后两次启动处理均保留这些新业务值、完整字节与修改时间，并保留原件、pending、raw 及事务记录。

旧 `restore.rollback` 没有上述持久对象身份。当前 Windows 路径不再据其旧标签自动删除、自动覆盖或递归清理；遇到旧现场会停止并保留，需人工核对。人工处理前应关闭可能写入的进程，完整保留活动 DB/WAL/SHM、旧保留区、pending 和 raw，分别用副本核查来源、版本、完整性与业务数据，再决定采用哪份资料库。本文不授权直接删除旧目录，也不把“重启后仍然停住”算作旧格式已自动迁移成功。

## API 依据与证据范围
